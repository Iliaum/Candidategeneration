# Avito Candidategeneration
Данный репозиторий содержит решение задачи генерации кандидатов (Retrieval) для поиска на платформе Авито. Решение достигает метрики **Recall@50 = 0.64** на скрытом тестовом наборе данных.

## Как запустить код и воспроизвести результат

Для того чтобы код отработал корректно и выдал итоговый файл `answer.csv`, необходимо подготовить окружение и данные:

### Подготовка окружения
Код написан под Python 3.9 или выше.
```bash
pip install -r requirements.txt
```

### Подготовка данных
Создайте в корне репозитория (там же, где лежит `solution.py`) папку с названием `dataset` с parquet-файлами:
- `train.parquet`
- `benchmark_items.parquet`
- `benchmark_queries.parquet`

Структура проекта:
```text
├── dataset/
│   ├── train.parquet
│   ├── benchmark_items.parquet
│   └── benchmark_queries.parquet
├── solution.py
├── requirements.txt
└── README.md
```

### Запуск скрипта
Запустите основной скрипт генерации:
```bash
python solution.py
```

**Результат:** После завершения работы в корневой папке появится файл `answer.csv`.

## Описание подхода к решению
### 1. Какие данные и признаки использовались и почему

В решении использовались следующие группы признаков:
- **Текстовые:** `search_query`, `item_title_raw`, `item_infm_params_text`, `item_description_raw`. Заголовок (`item_title_raw`) искусственно дублировался трижды при конкатенации текста. Это позволило сохранить максимальный приоритет точного совпадения главного интента, но при этом расширить словарь синонимов за счёт длинных описаний.
- **Географические и категорийные:** `search_location_id` и `search_category`. Услуги обладают высокой локальностью, поэтому совпадение гео-метки и категории применялось как жёсткий мультипликатор (x5 и x2 соответственно) к базовому текстовому скору BM25.
- **Исторические графовые:** факт клика на `item_id` по конкретному запросу из `train.parquet`. История использовалась как сильнейший поведенческий сигнал: если пользователи массово кликали на объявление по определённому запросу в прошлом, объявление получало экстремальный буст.
- **Глобальная популярность:** частота встречаемости `item_id` в `train.parquet`. Использовалась с логарифмическим сглаживанием как микро-вес для разрешения «ничьих» tie-breaking) при ранжировании кандидатов с одинаковым скором.

### 2. Какие модели или алгоритмы применены

Архитектура представляет собой гибридный ансамбль из методов информационного поиска (Information Retrieval) и графовых эвристик, работающий за $O(N)$:

- **Оптимизированный Okapi BM25:** в отличие от классического TF-IDF, BM25 использует логарифмическое насыщение частоты термина и штрафует за излишнюю длину документа, защищая алгоритм от SEO-спама в описаниях. Реализован кастомно поверх разреженных CSR-матриц `scipy.sparse` для эффективного использования оперативной памяти при перемножении.
- **Гео-зависимый инжектор (Bipartite Graph):** словарь, построенный на истории `train.parquet`. Позволяет за $O(1)$ получать список исторически успешных объявлений для пришедшего бенчмарк-запроса.
- **Two-Tower**: Эксперименты с семантическим поиском (Two-Tower архитектура на базе `rubert-tiny2` + InfoNCE Loss + FAISS) показали худший результат на кросс-валидации из-за нехватки Hard Negatives, поэтому в финальный инференс пошла строгая IR-эвристика.

### 3. Как проверялось качество решения до отправки

Для локальной валидации применялся кастомный **Overlap-Aware Validation Split**.

Случайное разбиение обучающей выборки давало неадекватно завышенный Recall@50 (утечка истории). Был проведён анализ тестового датасета `benchmark_queries.parquet`, который показал, что доля «знакомых» запросов (overlap) составляет ~14.7%. Был написан валидатор, который смешивал уникальные запросы (Cold Start) и запросы с историей в строгой пропорции 85.3% к 14.7%. Это позволило получить честную локальную метрику и тюнить гиперпараметры оффлайн.

### 4. Какие типы ошибок найдены при анализе и что с ними сделано

- **Ошибка «мёртвых» кандидатов:** алгоритм искал клики из старого `train.parquet`, которых уже не существовало в актуальном корпусе `benchmark_items.parquet`.
  - **Решение:** жёсткая фильтрация истории перед обучением (`train_df[train_df['item_id'].isin(valid_items)]`).

- **Гео-утечка (Geo-leakage) и слепота к «удалённым услугам»:** граф рекомендовал локальные услуги пользователям из других регионов просто по совпадению текста. При этом жёсткий фильтр по локации отсекал релевантные удалённые услуги (репетиторы, программисты).
  - **Решение:** граф перестроен с группировкой по ключу (Текст_запроса, Локация). Внедрена логика **Soft Fallback**: если запрос есть в истории, но локация не совпадает, объявление получает мягкий буст (+15), достаточный для выхода в топ только при высокой текстовой релевантности.

- **Out of Memory (OOM) при перемножении матриц:** оперативная память переполнялась при обработке сотен тысяч запросов на 190 тысяч объявлений (скрипт мог работать часами или падать).
  - **Решение:** алгоритм поиска переписан на батчевую обработку со сборщиком мусора (`gc.collect()`), а символьные N-граммы (Char TF-IDF) были исключены из финального пайплайна в пользу чистой скорости и стабильности BM25.
